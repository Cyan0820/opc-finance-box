# 开源发布与首批用户计划

## 发布目标

公开版本首先证明一件事：一个游戏公司可以在本地导入虚构或自有资料，得到有来源、可复核、不自动过账的月结差异包。

公开发布不是对生产成熟度的声明，也不以展示全部 Pack 和命令为首要目标。

## 对外一句话

> 开源、本地优先的游戏公司财务 Agent：把渠道结算、银行流水和项目成本整理成可由会计复核的月结差异与凭证候选。

## 首批用户画像

优先寻找同时满足以下条件的团队：

- 1–50 人的游戏或跨境数字内容公司；
- 创始人仍直接参与财务管理；
- 每月需要人工整理平台结算和到账；
- 已有外部会计或代账机构，可提供 baseline 和专业复核；
- 愿意先做只读 Shadow Close，不要求直接过账或申报。

暂不优先：大型集团、要求立即替换 ERP 的团队、无人提供专业复核的团队，以及首期就要求自动付款或无人申报的团队。

## 免费与付费边界

代码和本地演示保持 MIT 开源。商业收入可以来自：

- 首次部署和资料结构审计；
- 现有科目、主体与渠道映射；
- 合法授权的定制 Connector；
- 连续 Shadow Close 运行支持；
- 外部会计协作和证据包整理；
- 多用户、托管、备份、升级和生产运维。

免费使用不承诺会计结论、税务意见、数据修复、生产 SLA 或长期人工实施。

## 自有公司首个案例

1. 选择一个法律主体和一个已完成人工月结的月份。
2. 固定资料范围：渠道结算、银行流水、必要成本和现有会计结果。
3. 系统只读运行，不修改正式账。
4. 记录数据准备、Agent 执行和会计复核耗时。
5. 分类全部差异：来源缺失、映射、截止、会计政策、系统缺陷或接受范围。
6. 由外部会计独立复核。
7. 在下一自然月重复一次，拒绝只用单月成功声明成熟。

案例至少披露：

- 输入来源和覆盖范围；
- 人工与系统各自耗时；
- 匹配率、缺项和异常数量；
- Agent 错误与人工修正；
- 哪些动作始终由人完成；
- 数据经过何种脱敏，谁完成独立复核。

## 发布前检查

- README 的安装步骤在全新环境中实际通过；
- 演示只使用虚构数据；
- `git status` 不包含构建物、运行数据或临时文件；
- 使用独立工具扫描当前树和 Git 历史中的密钥；
- 完整单元测试、Pack audit、eval 和 doctor 通过；
- 仓库联系方式、漏洞报告渠道和 License 明确；
- 把 README 中的 `YOUR_REPOSITORY_URL` 替换为最终地址；
- 创建第一个版本标签时明确标注 `alpha` 或 `preview`。

## 发布后四周

成功指标不是 Star 数，而是：

- 至少 3 个陌生用户完成本地启动；
- 至少 1 个用户导入自己的脱敏结构；
- 收到安装、资料映射或月结流程的具体反馈；
- 找到 1 位愿意参与两个月 Shadow Close 的外部会计或财务伙伴。

在得到这些信号前，暂停新增国家和横向 Connector，把时间投入安装成功率、首个场景和真实复核。
