# 游戏样板平台化迁移地图

## 原则

迁移采取“先建立契约、再移动实现、始终保持游戏样板可运行”的方式。不能先复制一套电商代码，也不能为追求通用而删除游戏行业判断。

## 抽取顺序

### 1. 主体与税务解耦

建立通用 `LegalEntity`：主体 ID、名称、地区、本位币、准则和税务登记。把增值税纳税人类型、中国申报周期等字段移入 CN 地区扩展；保留兼容读取，避免当前样板中断。

### 2. 项目与行业对象解耦

把通用成本归属统一为 `project_id`，游戏 Pack 再提供游戏生命周期、渠道和 KPI。Commerce Pack 提供商品、SKU、订单、仓库和履约维度。

### 3. 结算与收入来源解耦

建立通用 `CommercialTransaction`、`ChannelSettlement`、`Receivable` 和 `CashReceipt`。游戏渠道、DTC 和第三方电商平台分别完成源数据映射与行业规则。

### 4. 模板和工作流注入

上线模板、月结任务、分析卡片和确认问题由 Pack 注册，不在 `server.py` 或前端写行业分支。

### 5. 税务包版本化

每个地区包独立维护规则、来源、生效日期、表单版本和评测集。只有达到对应成熟度，产品才展示相应能力；缺包时仍可做账和准备证据，但不得生成虚假的税务结论。

## 下一里程碑

1. 游戏服务器挂载已完成的 Box bootstrap 与 service dispatch 契约。
2. 用通用主体对象兼容替换当前 `company_profile.py` 的单中国主体假设。
3. 将现有中国税务工作底稿实现继续收口到 `jurisdiction.cn_mainland` 服务，避免由游戏页面默认加载。
4. 继续让游戏演示记录补齐稳定 `entity_id`，管理合并视图保留主体来源与抵销状态。
5. 为 Commerce 增加真实支付渠道连接器、库存批次/履约导入和更多异常评测。

## 已完成的平台基础

- Box 与 Pack 组合校验。
- 通用法律主体注册表、法定范围和管理合并范围。
- 未归属主体或未知主体记录的质量阻塞。
- 运行时热加载、能力开关、税务成熟度和人工确认接口。
- Commerce/DTC 订单—结算—贡献利润确定性引擎。
- 中国大陆与新加坡 jurisdiction Pack 的版本化官方来源文件。
- 可追溯税务候选日历和属地配置任务。
- 从行业、渠道、实体和税务国家创建 Box 的简化脚手架。
- 可复现的 Box 编译锁、启用服务/工作流目录和上线检查清单。
- 框架无关的 Box bootstrap 与服务分发 API 契约。

游戏工作台服务器现已挂载 `GET /api/box` 与 `POST /api/box/services/dispatch`。前端和外部 Agent 可以读取相同 Box Context 与过滤后的服务目录；服务分发仍经过 Pack、capability、法律主体和 review gate 控制。游戏工作台的持久化目标 API 与通用 Agent 草稿服务并存，后者不会静默写入前者的审计状态。
