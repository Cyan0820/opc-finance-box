# 首客私有工作区初始化

`activation-init` 为一个已经验证的 Box 建立首家真实 OPC 的私有工件骨架。它只接受尚不存在的绝对路径，不覆盖现有目录；初始化成功后目录权限为 `0700`，文件权限为 `0600`。

```bash
opc-finance-box activation-init path/to/box.json \
  /absolute/new/private-root \
  --period 2026-08 \
  --facts-as-of 2026-08-14 \
  --prepared-by activation-preparer

opc-finance-box activation-workspace-verify \
  path/to/box.json /absolute/new/private-root

opc-finance-box activation-workspace-status \
  path/to/box.json /absolute/new/private-root \
  --as-of 2026-08-14
```

## 初始化内容

工作区按当前 Box 指纹、主体集合和网络 Connector Pack 范围生成：

- `tax/workpapers/`：每个法律主体一份尚未回答的税务适用性底稿；
- `tax/reviewed-source/` 与 `tax/reviews/`：分别接收复核输出和受控导入后的逐主体轮换；
- `connector-shadow/workpapers/`：按当前 Box 的主体和受支持网络 Connector 组合生成尚未填写的独立 baseline 底稿；Shopify + Stripe 使用月结 Shopify/跨处理器 profile 与独立 Stripe Balance/Payout profile，选择 Wise 时再增加独立银行流水 profile。八类 access-gated Connector 的权限 request 与 receipt 按 `Connector Pack + 法律主体` 共享：同一主体的月结与日结只探测一次当前账户和凭据；Wise/Xero 使用 token 与当前主体绑定切片，PayPal/WooCommerce/ShipBob/Amazon Seller 使用当前主体绑定切片与动态密钥别名值。同一表中的无关主体变化不会让该主体回执失效。每条 Pipeline 仍保留独立的月份请求、baseline、observation 与 review。Shopify 月结、Stripe、Wise、Xero、PayPal、WooCommerce、ShipBob 和 Amazon Seller 命令执行后还会在此目录分别生成主体/月份绑定的私有 live request，避免手写窗口或月末；八类 live observe 必须显式提交当前回执。Stripe-only、Wise-only、Xero-only、PayPal-only、WooCommerce-only、ShipBob 和 Amazon Seller profile 同样使用对应安全请求链，Airwallex 使用最小 webhook/refetch profile；
- `connector-shadow/baselines/`、`assessments/` 与 `reviews/`：初始化时保持为空，只有独立来源底稿显式 finalize、真实只读 Pipeline 比对和独立复核后才产生工件；
- `pilot/readiness/`、`handoff/` 与 `registrations/`：首家准入、资料交接和首次运行登记；
- `pilot/shadow-baselines/` 与 `shadow-reports/`：存放含金额的人工关账 workbook 和未签认对比结果，不与正式复核目录混用；
- `pilot/entity-reports/`、`portfolio/` 与 `observations/`：只在真实逐主体复核、多主体组合和首次观察完成后接收对应工件；
- `pilot/series-periods/`：由操作者按规定目录合同准备至少两个连续月的完整证据；
- `pilot/period-workspaces/`：首期归档后由 `pilot-shadow-next-period-init` 按自然月逐次生成；初始化时不预造未来期间；
- `pipeline-runs/`：后续私有运行台账；
- `promotion/evidence/` 与 `promotion/ledger/`：分别存放待填写的晋级证据和追加式评估/复核台账；`artifact-paths.env` 会把后者声明为 `OPC_STABLE_PROMOTION_ROOT`，供完成写入后由 Readiness 只读投影；
- `runbook/`：初始化为空；首次记录进度时创建追加式、可校验的非权威操作者事件链；
- `artifact-paths.env`：只含工件路径，不含 Connector 密钥；其中 `OPC_ACTIVATION_WORKSPACE_ROOT` 可供 Workbench 只读投影后续月份和 Runbook 恢复位置；
- `commands.json`：带 `REPLACE_WITH_...` 占位符的参数数组和等价 shell 预览；
- `activation-workspace-manifest.json`：只含相对路径和初始化边界，不泄露私有根路径。

初始化不会创建税务复核、适用性登记回执、Connector baseline、Connector review、真实资料清单、运行结果或晋级批准；不会接受凭证、复制财务源文件、运行命令或触发外部动作。税务底稿、Connector baseline 底稿和首家准入底稿可以由操作者在私有目录内填写，其余初始合同文件不可改写。Connector 底稿只含空计数、空布尔控制和独立来源声明，不能用 Pipeline 自己的输出回填 baseline。

## 验证与状态

`activation-workspace-verify` 重新验证 Box 指纹、主体和 Connector 范围、目录及文件权限、符号链接、文件数量/大小、不可变文件哈希、逐主体税务底稿合同、Connector profile/主体/期间绑定、首家准入底稿的无密钥/无金额边界，以及完整命令清单与当前 Box 模板的一致性。它兼容 workspace schema v1–v4；新初始化使用 schema v5，把权限探测按 Pack + 主体去重，命令链仍为 command schema v2。v4 既有工作区继续使用旧的逐 Pipeline 权限路径与命令合同，不会被 v5 模板静默重写。它只返回计数、布尔状态与指纹，不返回私有路径或内容。

`activation-workspace-status` 进一步把当前目录内真实存在的复核工件交给原有十一阶段验证器，并返回与 `activation-status` 相同来源的当前工作波次。schema v5 还附带 connector access registry schema v3：每个 Pack + 主体只显示 `not_initialized`、`awaiting_current_credential`、`ready_for_authorized_probe`、`current`、`renewal_due`、`renewal_required` 或明确失败关闭状态，以及安全计数；它会用当前凭据引用重新绑定并检查回执时效，但不访问网络，不返回私有路径、账户、凭据/指纹或财务值。默认到期前 7 天进入 `renewal_due`，Workbench 显示剩余天数和 `connector-access-receipt-renew`；范围在到期前仍可用于有界 Shadow，续期也不会自动执行。到期或密钥轮换后进入 `renewal_required` 并关闭 dispatch。`blocked_invalid_receipt` 要求隔离篡改/无效回执后重新探测，不得用续期掩盖。`current` / `renewal_due` 都只表示此刻具备有界 Shadow dispatch 条件，不是 Shadow 已完成、财务勾稽通过或 Stable 晋级证据。

同一状态响应还包含 `connector_access_alerts`：稳定 alert ID、warning/critical 计数和不含私有值的下一动作。`connector-access-alerts BOX.json PRIVATE_ACTIVATION_ROOT --as-of YYYY-MM-DD` 可供外部 daily job 消费相同候选；它不安装调度、不联网、不发送通知。Workbench 只显示候选计数，实际接收人、时区、去重、恢复通知和升级路线必须由部署者显式配置。

目录型 Readiness 输入使用明确白名单，只包含税务适用性轮换、Connector Shadow 轮换、逐主体 Shadow 报告、连续期证据根和 Stable 晋级账本；`pipeline-runs/` 通过独立参数传入，Runbook 与其他私有目录不会被转发。这样逐主体观察、连续期复核和追加式晋级账本能在同一首客工作区内被重新验证，而不是在后半段永久显示“未挂载”。空目录会保持对应门禁未完成；空晋级目录以只读方式显示“尚无评估”且不会生成锁文件或事件文件。把文件放进目录本身不会使门禁通过，仍必须通过原始权限、内容、指纹、职责分离和 hash-chain 验证。

## 完整命令链

command schema v2 按依赖输出可修改步骤，而不是只停在首家准入：

```text
逐主体税务适用性
→ Connector 独立 baseline / 私有请求生成与验证 / 真实只读比对 / 复核
→ 首家准入复核
→ 资料交接
→ 每主体 Pipeline attempt 与首次登记
→ 每主体人工 Shadow Close 与独立复核
→ 多主体 portfolio（仅多主体 Box）
→ 首次 observation
→ 逐期间验证并事务性归档到 series-periods
→ 从最新已验证归档生成下一自然月增量工作区
→ 至少两个连续月 series
→ selected Pack 晋级证据、评估、记录、独立复核和 ledger 校验
```

每条 `run_cli` 同时保存 `argv` 与由同一数组生成的 `shell_preview`，初始化验证会检查二者完全等价。含 `REPLACE_WITH_...` 的命令标记 `requires_operator_edit=true`。所有带决定枚举的模板使用 `needs-correction` 或 `needs_more_evidence` 作为可解析的失败关闭默认值；操作者只能在真实证据支持时改成通过或批准。首次观察之后使用 `pilot-shadow-period-archive` 重新验证并归档每期单/多主体证据；归档放行下一期后，使用 `pilot-shadow-next-period-init/verify` 从最新月份自动推导并绑定新月份。多主体命令会自动枚举逐主体报告并强制 portfolio。完整月度操作见 [连续 Shadow 下一期间工作区](连续Shadow下一期间工作区.md)。正式 `entity-reports`、`observations` 和 `promotion/ledger` 在首期初始化时均为空。

处理首期总链时可用 `activation-runbook-record/status/verify` 记录和恢复操作者报告的进度；进入后续月份后，每个 `pilot/period-workspaces/YYYY-MM/runbook/` 使用 `pilot-shadow-period-runbook-record/status/verify` 形成独立的期间绑定事件链。两类 Runbook 都不改写 `commands.json`，不执行命令，不返回人员或证据引用，也不影响十一阶段权威门禁；完整契约见 [首客激活 Runbook](首客激活Runbook.md)与 [连续 Shadow 月度 Runbook](连续Shadow月度Runbook.md)。

## 操作边界

1. 私有根目录必须位于真实的、非符号链接父目录下，且在初始化前不存在。
2. `artifact-paths.env` 可以由本地 shell 或服务管理器读取，但 Connector 凭证必须来自独立 secret manager，不能追加到该文件。
3. `commands.json` 是操作清单，不是自动化批准。替换占位符后仍需由职责分离的操作者和复核人分别执行。
4. command schema v2 的普通 Connector 命令按 `complete → finalize → assess real read-only result → independent review` 排列；Shopify 月结和 Stripe Balance/Payout→银行链在 assess 前增加 `request-init → private edit → request-verify → access-receipt-verify → safe observe`；Wise、Xero、PayPal、WooCommerce 与 ShipBob 增加无需人工编辑的 `request-init → request-verify → access-receipt-verify → safe observe`。Amazon Seller 同样无需编辑 JSON，但必须先把 request-init 命令中的 `REPLACE_WITH_MARKETPLACE_ID` 替换为本次唯一 Marketplace；该值只进入私有请求，observe 前也必须验证当前 Amazon Seller access receipt。fixture/demo 即使计数相同，也因没有真实 API 网络读取和精确月份范围而不能通过 schema v2 source match。
5. 初始化结果不代表受限 Shadow、稳定版晋级、入账、付款、法定关账或外部申报获批。
6. Box 配置、主体、能力包或地区规则升级后，先运行 `upgrade-check`；初始化合同改变属于需要阻断复核的生产准备度变更。
