# 统一资料识别与证据关联

统一资料入口把 Excel/CSV、PDF 和图片先变成可复核候选，再由人确认事实边界。它不是“上传即入账”的黑盒。

## 银行 PDF / 图片对账单

1. 上传时选择法律主体；未确认主体时不自动识别。
2. 本地读取 PDF 文字层；扫描件或图片在本机具备 Tesseract/Poppler 时进入 OCR。
3. 仅提取同时含交易日期和金额的候选行，并保留日期、流水号、交易对手、摘要、收支方向、币种、金额、余额及字段证据。
4. 缺流水号、方向或币种的候选保持阻塞，不猜测。
5. 财务人员逐页对照原银行文件，补正候选并写明核对依据。
6. 只有原件确认和关键字段检查均通过，才开放“确认入台账”；正式台账仍保留 `entity_id`、`source_document_id` 和审计事件。

当前识别是保守的版式启发式，不等于银行接口数据，也不会核验账号归属或银行电子签章。首家公司应把真实版式加入脱敏回归样本。

## 发票 PDF / 图片

发票识别遵循相同的“候选 → 补正 → 原票确认 → 入台账”流程。对照原票只说明识别字段已经核对，不代表已完成税务机关查验、抵扣资格判断或会计入账复核；这些状态单独保留。

## 合同与验收/交付证据

合同和验收材料只提取文字并归档，不直接生成金额、验收结论或会计事实。用户只能把它们关联到同一 `entity_id` 的采购/验收记录：

- 关联会把 `document:<资料编号>` 和 SHA-256 证据写入采购记录；
- 不改变 `accepted_amount` 或 `acceptance_status`；
- 实际使用或接收成果的业务负责人仍须在统一确认队列中作出“全部验收、部分验收或退回整改”的决定；
- 全球管理汇总只展示关系，不能跨主体关联或代替主体审批。

## 收入结算核对底稿

经分流水、Apple/Google 财务报告、退款和差异核对表属于结算证据，不是第二份收入台账。系统将这类工作簿识别为“收入结算核对底稿”，保留行级差异和重要性判断，并且只允许关联同一 `entity_id` 的收入结算记录：

- 关联不会改写结算金额、回款状态或会计期间；
- 差异超过重要性阈值时进入异常队列，由财务解释时间差、退款、汇率或口径差；
- 同一底稿可以关联多个期间的结算，但每个关联关系都保留操作人、时间和说明；
- 管理合并可以查看核对状态，法定账仍按主体保留原始结算和复核证据。

## Agent 如何处理

- 未确认主体：阻塞并引导到资料入口。
- 银行/发票候选未核原件：阻塞入账，引导逐项补正。
- 合同/验收证据未关联：阻塞归档完成，引导选择同主体采购。
- 收入结算核对底稿未关联：阻塞证据归档，引导选择同主体结算；不自动生成或调整收入。
- 已关联证据：从资料待办移出，但对应采购仍保持原验收状态，直到有权业务负责人决定。

## 安全与上线边界

- JSON 入口全局限制约 28 MiB，无效 `Content-Length` 返回 400，超限返回 413；上传文件另有文件类型和大小限制。
- 本地 OCR 质量受扫描清晰度、语言包和版式影响，低质量材料必须人工录入或补正。
- 当前本地 JSON 存储没有跨文件数据库事务；多用户正式部署前应迁移到具备事务、权限、备份和不可篡改审计能力的数据库与对象存储。
