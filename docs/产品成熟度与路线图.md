# 产品成熟度与路线图

## 当前里程碑：可 fork 的技术 RC（真实投产成熟度仍为 preview / experimental）

当前版本已经形成完整的 Box 装配与运行契约：

- 业务范围：游戏、传统电商、DTC 独立站、第三方平台店铺。
- 渠道范围：App Store、Google Play、国内游戏渠道、DTC、Marketplace。
- 主体范围：单主体与多主体管理视图，法定账始终分离。
- 地区范围：中国大陆工作底稿级；AE、AU、CA、DE、FR、GB、HK、IE、JP、KR、NL、NZ、SG 和 US 安装了版本化设计级 Tax Pack；其他国家可由脚手架扩展。
- 数据入口：CSV、XLSX、受限 PDF/OCR、本地可编辑 API Connector，以及 Stripe、PayPal、Shopify、WooCommerce、Amazon Seller Orders v2026 / FBA 当前库存 / Finances 三源、Xero、Wise Business、Airwallex、ShipBob 的受限真实只读 API Connector。
- 交付形态：wheel、CLI、工作台服务器、Pack 目录、Box 配置、编译 Bundle、Handoff 私有工作区，以及严格白名单、带全量测试和 manifest 的可 fork Source Kit。
- 本地试用：`trial-init/verify/onboarding/run` 将一个行业、纳税国家和 integration 选择直接组装为 demo 工作区；不可变 Handoff Box 与版本化运行数据分离，启动前后联合重验，默认只监听回环地址且不读取 Connector 凭证。Founder onboarding 投影把完整 setup contract 压成五段旅程、当前下一步、优先阻塞项和可复制命令模板，但不记录完成或推断生产就绪。
- 自助装配：浏览器与 CLI 共用 45 个已校验 Starter；单/多主体可逐主体选择 Tax Pack 与数据源，生成完整 Connector 绑定、严格配置、可复现 CLI 和确定性 Handoff；浏览器在保存前校验实际 ZIP 字节 SHA-256，可下载非签名 JSON 收据并由 CLI 与正式 ZIP/manifest/安装 Pack 联合复核，不切换活动运行时。
- 技术 RC：`release-candidate-audit` 实际生成并逐成员复现 3 profile × 15 纳税地区的 45 个 Handoff，另行编译全部 19 个 profile-scoped 集成变体、3 个双主体变体、Finance Eval 和部署资产；可选择把 wheel 与 Source Kit 绑定到同一次矩阵审计。技术 RC 只证明可交付产品矩阵，不替代真实客户证据或 Stable 晋级。
- 生产化状态：统一十一阶段 Readiness Matrix 聚合能力包契约、税务时效/适用性、数据连接器配置、真实 Connector Shadow Pack 覆盖、首家准入、交接、观察、连续期证据与追加式 Stable candidate 批准；最后一阶段从 `OPC_STABLE_PROMOTION_ROOT` 只读验证 hash chain 和当前 Box/Pack/version，全部目标 Pack 通过才开放源码晋级准备门。首客 workspace 状态重算已能通过目录白名单消费逐主体报告、连续期证据和晋级账本，不再在后半段丢失已完成证据；聚合状态仍不是 Pack manifest 变更、发布或申报批准。

Pack 审计的 `complete_implementation=true` 只代表 manifest 中每项 capability 都有 service、connector 或 runtime guardrail；它不代表生产成熟。当前没有 Pack 标为 `stable`，因此 `stable_release_ready=false`。

仓库现已提供首次观察复核、单/多主体期间证据验证后事务性归档、至少两个连续月份的源证据重验与独立连续性复核，并由 `promotion-assess` 强制再次验证该连续期收据、精确绑定同一批逐主体报告与多主体组合签认；同时具备追加式签认账本和职责分离控制。但还没有代表性真实公司脱敏 Shadow Close 证据，因此不得把“控制已实现”解释为“Pack 已成熟”。

## 下一阶段验收门

### Preview → stable

每个 Pack 独立满足：

1. 契约版本与迁移策略明确，旧 Box lock 能检测兼容性。
2. 正常、边界、缺资料、重复、跨主体、跨币种和规则过期场景都有评测。
3. 代表性真实业务脱敏样本完成 shadow run，结果由财务专业人士逐项签认，并达到经批准且不低于产品底线的覆盖与匹配阈值。
   该样本必须覆盖至少两个连续自然月，并通过独立连续性复核；归档后的下一期工作区从最新已验证月份推导，且重新生成 period-bound readiness/handoff；stable 评估会再次验证全部期间源文件和 Pipeline 台账，拒绝单期、缺月、替换文件或连续性复核人与证据角色重叠。
4. 所有 mutating / external 动作经过认证授权、幂等、审计和恢复测试。
5. 运行、备份、恢复、升级和回滚有可演练手册。

多主体 Box 还必须在逐主体 Shadow Close 之外形成组合验收包：所有已配置主体同期间覆盖、每份报告当前签认、月结来源运行通过台账指纹核验、显式汇率底稿可追溯，并由不同于所有逐主体复核人的组合复核人签认。仓库已提供 `shadow-close-portfolio-assemble/review/verify` 工具，并由 `promotion-assess` 对每个样本期间机器校验验收包与逐主体原始报告的绑定；在真实脱敏样本尚未完成前，它只代表验收能力已就绪，不代表 Pack 已达 stable。

仓库内置的声明式边界评测可直接运行：

```bash
opc-finance-box eval evals/core_packs.json
```

Eval runner 只允许 `read` 和 `draft` Service，不执行 mutating/external 动作。Bundle 中的 `release-gates.json` 同时列出单测、provider audit、eval、doctor、upgrade check 和必须由人完成的 shadow close/恢复演练；其初始 `release_status` 永远是 `not_approved`。

编译 Bundle 还会生成 `stable-promotion-policy.json`，把最低 Shadow 覆盖、必须自动门、恢复演练、职责分离和只产生 `stable_candidate` 的边界绑定到 Box fingerprint。完成真实证据后执行：

```bash
opc-finance-box promotion-assess BOX.json promotion-evidence.json
opc-finance-box promotion-record BOX.json promotion-evidence.json \
  --actor promotion-preparer --promotion-root /var/lib/opc-finance/release_promotion
opc-finance-box promotion-review BOX.json ASSESSMENT_ID \
  --decision approved --actor independent-release-reviewer \
  --rationale "已复核 Shadow、自动门、职责分离与恢复演练" \
  --evidence-reference release-review-record \
  --promotion-root /var/lib/opc-finance/release_promotion
```

详细证据 schema、不可降低的阈值与源码状态变更边界见 [Stable 晋级证据与签认](Stable晋级证据与签认.md)。

编译 Bundle 的 `upgrade-policy.json` 记录兼容性边界。升级前执行：

```bash
opc-finance-box upgrade-check path/to/current-box.json path/to/previous/box.lock.json
```

无变化返回 0；存在需复核但非破坏性变化仍返回 0 并列出 review 项；主体控制、服务/review gate、capability、Connector 或工作流发生破坏性变化时返回 4。任何非空变化都应先完成 shadow run。

### Tax workpaper → filing_assist

除上述条件外，还必须限定具体税种、地区、登记类型、表单版本和外部系统；保持有权人批准与实际回执，不把 `filing_assist` 解释为无人值守申报。

## 建议扩展顺序

1. 先接真实但只读的数据源：支付平台、银行导出、平台结算和会计系统导出。
2. 用 shadow close 比较现有人工结果，积累异常样本和 Pack eval。
3. 把稳定的映射与确定性规则固化，保留证据和人工判断。
4. 最后才考虑过账、付款或外部申报，并逐个动作增加授权与恢复能力。

这个顺序也适用于新增国家：先设计/证据，再日历/工作底稿，最后才是特定流程的 filing assist。
