# Build OPC Finance Box

Build from Pack contracts; do not clone industry-specific ledgers or infer tax support from a country code.

## Workflow

1. Locate the repository root containing `pyproject.toml`, `packs/`, and `examples/boxes/`.
2. Run `python -m src.cli options` and `python -m src.cli box-starters`; select only installed Pack IDs and use a contract-checked Starter when the requested product/country pair exists. When the user wants the standard single-entity starting point, prefer `starter-init /absolute/new/root --profile PROFILE --country CC --actor RECIPIENT` and only add integration presets listed for that Starter. For 2–20 legal entities under one product Profile, prefer `starter-compose /absolute/new/root --profile PROFILE --entity CC=entity_id ... --entity-integration entity_id=PRESET --reporting-currency CCC --actor RECIPIENT`; bind each external source only to the legal entity it actually serves, keep every entity's Tax Pack and books separate, and never treat the reporting currency as an FX rate or consolidation authorization. Do not use a global Shopify or Stripe integration in a multi-entity Box while the provider implementation uses one runtime credential.
3. Create or edit a human-oriented spec under `examples/box_specs/`:
   - Keep business model, channels, connectors, features, and tax country orthogonal.
   - Create one entry per legal entity with functional currency, accounting basis, fiscal year end, tax Pack, and registrations.
   - Require reporting currency for multiple functional currencies.
4. Run `create`, `validate`, and `compile`; do not hand-edit a compiled lock.
5. Run `doctor`, `pack-audit`, and `eval evals/core_packs.json`.
5.1. When delivering a self-service fork, run `handoff-bundle SPEC.json --output NEW.zip`, then `handoff-verify NEW.zip`; verify the returned SHA-256, require installed-Pack reproducibility, and never overwrite an existing delivery. When a browser `.browser-receipt.json` accompanies the ZIP, set both files to mode `0600` and run `handoff-receipt-verify NEW.zip RECEIPT.json`; this reruns formal Pack reproducibility and binds the safe receipt fields, but cannot attest browser execution or identity. A recipient may run `handoff-unpack NEW.zip /absolute/new/workspace --actor RECIPIENT` and `handoff-unpack-verify /absolute/new/workspace`; treat every receipt as local integrity metadata, never as a signature or financial evidence.
5.2. When delivering the editable product implementation rather than one Box configuration, run `source-kit-bundle --output NEW-SOURCE.zip`, then `source-kit-verify NEW-SOURCE.zip`. For a local recipient workspace, prefer `source-kit-unpack NEW-SOURCE.zip /absolute/new/fork --actor RECIPIENT`, then `source-kit-unpack-verify /absolute/new/fork` before any edit, dependency install, command execution, or `git init`. Preserve the strict allowlist and explicit exclusions; do not add Git history, runtime data, private evidence, vendored dependencies, build outputs, or credentials to make the archive look more complete.
6. For a real first-customer activation, run `activation-init` once against a new absolute private root, verify it with `activation-workspace-verify`, and follow the generated dependency-ordered command chain through handoff, registered Pipeline attempts, per-entity Shadow Close, multi-entity portfolio when applicable, first observation, consecutive periods, and selected-Pack promotion. Use `activation-runbook-record/status/verify` only to preserve operator continuity; a reported-complete Runbook step is never authoritative stage evidence. Complete only generated workpapers and placeholders. Keep every generated fail-closed decision until real evidence supports changing it. Connector baseline workpapers must be independently prepared from real source evidence, then explicitly finalized, assessed against a real read-only Pipeline result, and independently reviewed. Never treat initialization, a fixture run, an unfinished workpaper, or Runbook progress as review evidence or a Connector baseline.
7. For Boxes with network Connectors, run `connector-shadow-status` against the private reviewed-artifact rotation, then run `production-readiness` and `activation-workspace-status`; report each failed evidence stage and the dependency-safe current work wave without exposing private artifact paths.
8. If replacing an existing build, run `upgrade-check` against its `box.lock.json`.
9. Report internal-demo readiness separately from bounded Shadow, stable release and external-filing readiness.

Use the exact commands and output contract in [references/box-workflow.md](references/box-workflow.md).

## Controls

- Keep statutory books, bank accounts, tax workpapers, and approvals inside one `entity_id`.
- Import bank statements with stable transaction IDs, masked account references and explicit direction/currency; source mapping and account-level balance reconciliation remain separate human gates.
- Import accounting trial balances with stable entity-period-currency-account keys and evidence; validate debit/credit and roll-forward controls per currency, while keeping mapping/completeness, posting and period close as separate human-controlled states.
- For Xero Trial Balance, bind each Box entity to exactly one environment-configured tenant and organisation, verify Organisation ID and base currency before reading the report, and accept only a fixed point-in-time GET. Preserve YTD columns separately; never infer opening or period movements, and do not feed that snapshot into GL movement reconciliation or month-close controls that require them.
- For Wise Business balance statements, bind each Box entity to one exact BUSINESS profile and each functional currency to one balance using environment-only configuration. Pin the Global API version and fixed read-only endpoints, require a half-open UTC window, validate the statement query echo and running balances, hash raw source identifiers, and allow only masked account references and allowlisted details. Enforce personal-token jurisdiction eligibility or explicit partner approval; fail closed on SCA. Wise may replace the bank-file source in reconciliation/First Close/month close, but never GL, Trial Balance, payment or posting.
- For Airwallex expenses, bind each Box entity to one exact legal entity and account using environment-only scoped credentials. Pin the date API version, read only APPROVED expenses in a half-open created-at window, hash raw identifiers and omit card, person, comment and attachment details. Convert amounts to configured integer minor units without rounding. After the first checkpoint, refetch a bounded overlap using the stable business key and record-version hash while keeping the logical checkpoint monotonic; the sync plan must explicitly deny complete update capture. Treat source sync status as evidence only; never call the sync endpoint or infer accounting mappings, approval, posting or payment. Keep the Pack experimental while the API is Beta and until a signed, idempotent Spend webhook recovery path and real update-capture Shadow evidence exist.
- For ShipBob fulfillment evidence, bind one environment-only credential to exactly one Box legal entity unless the provider is forked to implement explicit per-entity credential references. Pin the official API version and fixed production/sandbox hosts, build bounded integer order `Page` and return `Cursor` values locally, treat the response `next` URL only as a next-page signal and never follow or reuse it, and cap half-open incremental windows at 31 days. Hash all source and tracking identifiers; retain destination country, bounded operational status and SKU only, never customer identity, address or raw tracking. Treat fulfillment invoices and return dispositions as review candidates, not revenue, inventory movement, AP, posting or external-action evidence. A return may validly reference a shipment outside the current window; preserve that exception without blocking the batch, while same-window orphan shipments and return items fail closed.
- For PayPal Transaction Search evidence, bind one environment-only Client ID/Secret pair to exactly one Box legal entity unless the provider is forked for explicit per-entity credential references or compliant Partner access. Use only fixed production/sandbox OAuth and reporting hosts, exchange/cache access tokens in memory, request `transaction_info` and balance-affecting records only, paginate locally, and reject more than 31 days or 10,000 records. Hash transaction/reference IDs and drop payer, address, item, invoice, free-text, merchant-account and response-link fields. Preserve T-code, transaction and fee currency separately; treat refunds, reversals, fees and withdrawals as processor review candidates, never revenue, tax, bank reconciliation, journal, posting or external-action evidence.
- For WooCommerce order/refund evidence, bind one environment-only site origin and read-only Consumer Key/Secret pair to exactly one Box legal entity unless the provider is forked for explicit per-entity credentials. Use fixed `/wp-json/wc/v3/orders` and `/refunds` collection paths over HTTPS Basic auth, build bounded integer pages locally from `X-WP-Total*`, and never follow response links. Read modified order snapshots and created refund events in a maximum 31-day half-open window; hash order/refund/transaction IDs and drop customer identity, address, IP/User-Agent, notes, product names/SKUs/IDs, meta and response links. Preserve currencies separately and treat status, paid timestamps, destination tax evidence and refunds as review candidates, never settlement, revenue, tax liability, inventory movement, posting or external actions.
- When Wise completes a Shopify + Stripe order-to-bank chain, dispatch it as a fourth Connector rather than accepting duplicated direct bank rows. Convert major-unit bank amounts to configured integer currency minor units without rounding; preserve the Wise batch in lineage and keep payout-to-bank matches review candidates.
- Before accepting a live four-source chain, compare it with an independently prepared Connector Shadow baseline covering every source record count and supported cross-source control. Bind the complete private baseline and Pipeline result by SHA-256 while persisting only counts/booleans, and require a reviewer different from the baseline preparer. Do not treat the Pipeline's own output as its independent baseline.
- Before promoting a selected network Connector Pack to a stable candidate, require one current reviewed Connector Shadow artifact for every bound sampled entity-period and require the artifact to explicitly cover the target Pack. Revalidate Box, entity binding, scope, hashes, freshness and role separation; persist only safe summaries, never private artifact paths or source/control details.
- Mount current schema-v2 reviewed Connector Shadow artifacts through one absolute `0700` rotation directory with `0600` regular files. Reject symbolic links, stale or future reviews, non-passed decisions, duplicate pipeline/entity/period scopes, unexpected entries and incomplete selected network Pack coverage. A registry pass is Pack-level readiness evidence only; stable promotion must still revalidate the exact sampled entity-period set.
- Import external general-ledger lines with stable journal/line identities; balance each journal per currency, reconcile account movements to the trial balance, and require explicit account-to-statement mappings. Never infer mappings or write the external export into the internal ledger.
- For three-way month-close control, bind every masked bank account/currency to one explicit Trial Balance GL cash account and the current bank source fingerprint. Derive the ledger balance from Trial Balance, require evidence-backed reviewed reconciling items, and never treat equal balances as transaction matching, posting, or close.
- For a first close, run source discovery before asking the user to author mappings. Preserve exact source account names and fingerprints, expose all same-currency GL options without ranking them, and emit `REPLACE_WITH_...` starters that preflight must reject until reviewed.
- For a multi-entity month-close portfolio, require one same-period `finance.month_close_control` candidate and source-run evidence per selected entity. For recorded or live use, verify each supplied summary against the tamper-evident run ledger's safe source fingerprint and completed review gates; never persist the raw Pipeline result just to make this link. Preserve every native-currency summary, translate only with period-specific approved rates and evidence, and suppress the portfolio total when any entity or FX control is blocked. Keep the result pre-elimination and never call it a statutory consolidation.
- For multi-entity Shadow Close acceptance, require one current accepted single-entity report for every configured legal entity and the same period, then bind them to a ledger-verified ready portfolio by fingerprints only. Persist no report or portfolio amounts in the acceptance manifest, require a portfolio reviewer distinct from every entity reviewer, and require stable-promotion evidence to carry exactly one verified manifest per sampled period while persisting only its safe summary. Treat the output as real-sample evidence rather than automatic stable promotion.
- For the first real pilot observation, bind the current Pilot readiness, data handoff and Shadow Run registration to every current reviewed entity Shadow report. A multi-entity Box must also bind one reviewed portfolio whose source attempt set exactly matches the registration. Require the final observation reviewer to differ from the registrar, every entity reviewer and the portfolio reviewer. Persist no financial values; any `system_defect` must produce `needs_correction` and block the next Shadow period. A passed observation never promotes a Pack or authorizes posting, payment, close or filing.
- Before preparing stable-promotion evidence for a real pilot, reverify 2-24 consecutive calendar-month observation periods from an exact private directory layout. Bind each period's current readiness, handoff, registration, Pipeline ledger, entity reports, portfolio when applicable, and observation review by aggregate content fingerprint without persisting values or paths. A blocked period cannot be followed by another period. Require the continuity reviewer to differ from every period principal. Approval only permits evidence preparation; it never creates a stable candidate or authorizes a financial action.
- Stable-promotion assessment must reverify that reviewed consecutive series and require its exact periods, entity reports, and multi-entity portfolio manifests. Reject single-period thresholds, substituted reports, stale/tampered source files, and any continuity-reviewer overlap with promotion evidence roles. Persist only a no-path, no-source-hash, no-value series summary and the separation principals.
- Never add amounts across currencies without explicit rates, periods, and sources.
- Treat `draft`, `approved`, `posted`, `closed`, and `filed` as distinct states.
- When Commerce is enabled, keep order refunds, return authorization, warehouse receipt and disposition as separate evidence; restockable goods remain review candidates until an approved inventory action.
- Keep import declaration value, freight, insurance, duty, import tax and brokerage separate; never infer customs classification, duty rate, tax recoverability or posting from a landed-cost candidate.
- Keep generated jobs disabled until an operator configures scope, timezone, idempotency, alerting, and owners.
- Never interpret complete provider coverage as `stable` or `filing_assist`.
- Do not enable mutating or external actions merely to make an eval pass.

## Expected handoff

Return the strict Box config, compiled Bundle path, selected Packs/entities, doctor/eval/upgrade results, blockers, and explicit next human gates. Preserve product maturity warnings.
